# Roadmap — RAVEN

## Current State
- The pipeline works end-to-end (plan → data collection → hybrid analysis → narrative → PDF report → delivery) when given a valid `OPENAI_API_KEY`. This was re-verified with a real end-to-end run against the live OpenAI API (`gpt-4o-mini`): a real hypothesis was submitted through the FastAPI API, all six stages completed, and a real 2-page PDF investment memo was produced and retrieved via `GET /v1/hypotheses/{id}/report`. 34 pytest tests pass with the LLM and YFinance layers stubbed out, plus 2 opt-in integration tests (skipped by default) that exercise the real Yahoo Finance API.
- `LangGraphValidationOrchestrator` has been renamed to `SequentialValidationOrchestrator` with a docstring stating plainly that it is a sequential `if/elif` stage dispatcher, not a LangGraph `StateGraph` (a backward-compatible alias is kept). The Temporal-era `workflows/definitions.py` / `workflows/activities/` modules are still present and still not part of the live path.
- `PythonSandbox` now runs LLM-generated code with a restricted builtins allowlist (`open`/`eval`/`exec`/`compile` absent, `import` guarded to a fixed analysis-module allowlist) and a wall-clock execution timeout, instead of bare `exec()` against real `__builtins__`. See "Phase 1" below for what changed and why the allowlist ended up including a guarded `import` rather than blocking it outright.
- Hypothesis records are held in `InMemoryHypothesisRepository`; a process restart silently discards all submission/status history even though on-disk artifacts (plans, data, charts, PDFs) survive.
- OpenAI is the only LLM provider, wired directly into `langgraph_pipeline.py` and `llm.py` — there's no provider abstraction beyond the already-defined `BaseLLM` interface being used for exactly one implementation.
- CI now runs `pytest -q` and `ruff check .` on every push/PR to `main` (`.github/workflows/ci.yml`); `ruff check .` is clean.

## Phase 1 — Near-term (weeks)

### Done
- **Sandboxed `PythonSandbox` execution.** `PythonSandbox` (`orchestration/python_sandbox.py`) no longer executes LLM-generated code against real interpreter `__builtins__`. It now takes an `allowed_builtins` allowlist (`SAFE_BUILTINS` from `langgraph_pipeline.py` is now actually plumbed in, via `allowed_builtins=SAFE_BUILTINS` in `_run_analysis_code`) and enforces a wall-clock timeout (`AppSettings.sandbox_timeout_seconds`, default 15s) by running code on a background thread and raising `SandboxTimeoutError` if it doesn't finish in time. `open`, `eval`, `exec`, and `compile` are absent from the allowlist outright.
  - One deliberate design change from the original plan: `import`/`__import__` is **not** blocked outright. A real end-to-end run against the live OpenAI API showed that GPT-4o-mini's generated analysis code routinely writes `import json` / `import pandas as pd` at the top of its own snippet — even though those names are already bound by the trusted preamble — and simply removing `__import__` broke the real pipeline (5/5 retries failed with `__import__ not found` before this was caught). The fix is a *guarded* `__import__` (`make_guarded_import` / `DEFAULT_ALLOWED_IMPORT_MODULES` in `python_sandbox.py`) that only permits a fixed allowlist of pure-computation/data modules (`json`, `math`, `statistics`, `re`, `datetime`, `decimal`, `itertools`, `functools`, `collections`, `pandas`); `import os`, `import sys`, `import subprocess`, `import socket` still raise `ImportError`. This is documented as a known, deliberate residual risk in `python_sandbox.py`: pandas' file/URL readers (`read_csv`, `read_json`, ...) do their own I/O and don't go through the sandbox's `open`, so a malicious completion could still coerce pandas into reading an arbitrary local path. Fully closing that would require running analysis code in a separate OS-level sandboxed process — not attempted here; tracked below.
  - Trusted, developer-authored setup code (the sandbox "preamble" that binds `load_json_artifact`/`write_json_artifact`/etc.) runs via a new `PythonSandbox.run_trusted()` with full builtins; only that explicit path bypasses the restriction, and it is never given model-generated content.
  - Verified with 16 new tests (`tests/test_python_sandbox.py`): legitimate numeric and pandas-style analysis code still works, and the roadmap's named attack shapes are blocked/time out — `__import__('os').system(...)`, `open('/etc/passwd')`, `eval`/`exec`/`compile`, `import socket`, and an infinite loop (bounded to a finite-but-long loop in the test itself so the unkillable daemon thread it leaks behind doesn't starve the rest of the test suite of CPU).
  - Re-verified with a real end-to-end pipeline run against the live OpenAI API: real LLM-generated pandas analysis code executed successfully in the hardened sandbox on the first attempt.
- **Orchestrator naming.** Renamed `LangGraphValidationOrchestrator` → `SequentialValidationOrchestrator` (in `orchestration/langgraph_pipeline.py`), updated all call sites (`workflows/hypothesis_workflow.py`, `workflows/activities/validation.py`) and tests. Added a docstring on the class and on the module explaining the actual execution model (plain `if/elif` dispatch over `_run_<stage>` methods; stage sequencing lives in the callers, not in this class) so nobody reading the code cold is misled again. A backward-compatible `LangGraphValidationOrchestrator = SequentialValidationOrchestrator` alias is kept at module scope in case another in-flight branch still imports the old name. Porting to a real `langgraph.graph.StateGraph` was considered and deferred (see "Deferred" below) rather than attempted half-done.
- **CI.** Added `.github/workflows/ci.yml`: runs `pip install -e ".[dev]"`, `pytest -q`, and `ruff check .` on push/PR to `main`.
- **Deprecation warnings.** Swapped `datetime.utcnow()` for `datetime.now(timezone.utc)` in `langgraph_pipeline.py`, and fixed the Starlette `TemplateResponse` deprecated argument order in `api/ui.py` (`request` now passed first). Both previously emitted `DeprecationWarning`s on every test run.
- **Lint cleanup.** `ruff check .` was at 20 pre-existing errors (unused imports/variables, one fixture-name redefinition, import-order-after-sys.path-hack in a script) with no CI enforcing it; all are now fixed so CI actually starts green rather than red on day one.
- **One Phase 2 item pulled forward:** added `tests/test_yfinance_integration.py` — two integration tests against the real Yahoo Finance API (company info, historical prices), marked `@pytest.mark.integration` and skipped by default (`RUN_INTEGRATION_TESTS=1 pytest -m integration` to run). Verified passing against live Yahoo Finance data.

### Still open
- Remove or clearly quarantine the dead Temporal-era code (`workflows/definitions.py`, `workflows/activities/`) — either delete it or move it under a `legacy/` package with a README note, and update `tests/test_workflow_activities.py` accordingly. Not attempted in this pass: `workflows/activities/validation.py` turned out to still be exercised by a genuine, non-trivial integration test (`tests/test_workflow_activities.py::test_pipeline_stages_execute`, which runs the full six-stage pipeline through the activity-wrapper call shape and asserts a real PDF gets produced) rather than being purely dead weight, so quarantining it needs a bit more care than a blind move-and-delete.
- Add retry/backoff around the `yfinance` calls in `yfinance_tools.py` — Yahoo Finance rate-limits aggressively and the current handlers have no retry, timeout, or graceful-degradation path if a ticker lookup fails mid-pipeline.
- Further sandbox hardening: the guarded-`import` approach above still allows `pandas` to read arbitrary local files via its own I/O (bypassing the blocked `open`) if a malicious completion tries. Closing this fully means running analysis code in a separate OS-level sandboxed process (a subprocess with its own restricted filesystem view, or a container), which is a bigger change than fits "Phase 1."

### Deferred (considered, not attempted)
- Porting `SequentialValidationOrchestrator` onto a real `langgraph.graph.StateGraph`. The current caller pattern (`HypothesisWorkflowClient` invoking one stage at a time via `asyncio.to_thread`, with human-review pause/resume and cancellation happening *between* calls) doesn't map cleanly onto a single compiled-graph invocation without risking a behavior change to pause/resume/cancel semantics that the existing test suite would not fully catch. Renaming to an accurate name (done, see above) was judged the safer, completable-with-confidence option for this pass; a real `StateGraph` port is left as future work if someone wants to take it on deliberately (it would need its own test plan for the pause/cancel edges, not just a mechanical rewrite).

## Phase 2 — Medium-term
- Replace `InMemoryHypothesisRepository` with a persistent store (SQLite via SQLAlchemy would fit the existing `ABC`-based `HypothesisRepository` interface with minimal churn) so hypothesis history survives restarts.
- Introduce an LLM provider abstraction beyond the unused-in-practice `BaseLLM` interface: add at least one second implementation (e.g. an Anthropic or local-model adapter) and make the choice configurable via `AppSettings`, removing the current hard OpenAI lock-in.
- Build an evaluation harness for report quality — currently there is no automated way to judge whether a generated executive summary, key findings, or risk list is actually good; even a small rubric-based LLM-as-judge or a golden-hypothesis regression set would let changes to prompts be validated instead of eyeballed.
- ~~Add integration tests that exercise the real `yfinance` calls (marked `@pytest.mark.integration`, skipped by default, run on a schedule)~~ — **done** (`tests/test_yfinance_integration.py`); wiring a scheduled CI job to actually run them periodically is still open.
- Expose workflow/report history and human-review actions in the web UI beyond the current single-page flow, and add basic auth so `/v1/hypotheses` isn't fully open when deployed.

## Phase 3 — Stretch
- Multi-tenant deployment: real authentication/authorization per `user_id`, persistent storage, and object storage (S3-compatible) for artifacts instead of local disk, so RAVEN can run as a shared service rather than a single-user local process.
- Pluggable data sources beyond Yahoo Finance (SEC filings, earnings call transcripts, alternative data) behind the existing `ToolSet`/`ToolHandle` protocol, so the planning stage can draw from a richer, provider-agnostic tool catalog.
- A proper async task/workflow engine (Celery, Temporal done correctly this time, or a real LangGraph graph) if concurrent multi-user load ever requires more than the current in-process `asyncio.create_task` model.

## Success Metrics
- **Phase 1**: CI is green on every PR (done); a fuzzed/malformed LLM code completion can no longer escape `PythonSandbox` for the attack shapes tested — `os.system`, raw file access via `open`, `eval`/`exec`/`compile`, `socket` (done, see `tests/test_python_sandbox.py`); a malicious completion still has a narrower residual path via `pandas`'s own file readers (open item, see above); a simulated Yahoo Finance rate-limit no longer crashes a live pipeline run (open — retry/backoff not yet added).
- **Phase 2**: hypothesis history survives a process restart (demonstrable via a restart-and-fetch test); at least two LLM providers can complete the full pipeline against the same hypothesis with comparable output structure; an evaluation run produces a numeric/qualitative score for report quality that can be diffed across prompt changes.
- **Phase 3**: a second concurrent user can submit and track a hypothesis independently without state collisions; at least one non-Yahoo-Finance data source is live in the planning stage's tool catalog.
